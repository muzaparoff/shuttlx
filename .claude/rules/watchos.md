# watchOS Rules

## General

- Scheme name: `ShuttlX Watch App`
- watchOS target path: `ShuttlX Watch App/`
- Build: `xcodebuild -project ShuttlX.xcodeproj -scheme "ShuttlX Watch App" -destination 'generic/platform=watchOS Simulator' build` (do NOT pass `-sdk` — it forces the iOS companion target onto the watch SDK and breaks its SPM deps)
- Background mode: `workout-processing` for active workouts

## Timer Display

- Use 40pt monospaced font for timer on watch (smaller than iOS 52pt)
- Use `DispatchSourceTimer` (not `Timer`) — drift-proof, works when screen off
- Must work during wrist-down (screen off) state
- Test with long workouts (30+ minutes)
- **Watch screens follow the timeline mockup** (2026-10, owner decision: "follow the mockup"; it replaced the 4-row free-run metric stack). Source of truth: the timeline mockup's 10 watch screens. If something doesn't fit, it visibly doesn't — fix the size, don't add a scale factor.

  - Keep the last line clear of the TabView page dots: `max(10, h * 0.055)` bottom inset (dot band y193–195.5 of 197 on 40mm, y240–245.5 of 248 on 46mm).
  - HR and the safety banner never leave the screen; any new running-page element must fit the 40mm budget with the banner showing — check with the snapshot harness.
  - No idle animations; any `TimelineView(.animation)` must pass `paused:`; AOD (`isLuminanceReduced`) shows `aodMinimalView` (time + BPM) only.

## Pace (Rolling vs Cumulative)

- Pace is computed from a **sliding 30-second window**, not cumulative average from workout start
- Guards: must be ≥20s into workout AND ≥0.05km total distance AND window ≥5s AND ≥5m moved, else shows "—"
- CMPedometer distance has ~30s warmup lag; first sample arrives skewed (e.g. 30s / 0.05km = 10'00). Sliding window avoids the warmup artifact entirely
- Root cause doc: `docs/incidents/2026-06-06-pace-10min.md`

## Controls

- Circular buttons: green for pause, red for stop
- Keep controls large and tappable (min 44pt touch target)

## Workout Lifecycle

- **Route to Health**: `HKSeriesType.workoutRoute()` is in the watch share types (`HealthKitAuthService.buildHealthKitTypes`); `finishRoute` needs it. Existing installs see the Health sheet once more (prewarm on launch). *Unverified on device: look for "HKWorkoutRoute saved" vs "Failed to finalize route" and a map in the Health app.*
- HealthKit workout session must survive app backgrounding
- Save workout data on pause AND on stop (crash recovery)
- If app is killed mid-workout, data must be recoverable from local storage
- **Checkpoint files**: the 15 s checkpoint writes `active_workout_backup.json` WITHOUT the route; the route goes to `active_workout_route.json` (tagged with the session id) at most every 60 s and on every pause checkpoint (`WorkoutPersistence.checkpoint(_:route:)`). `recoverCrashedWorkout()` merges them (an inline route from an older build wins); `clearBackup()` deletes both. A kill loses at most 60 s of route points.
- **Peak HR is active time only**: a sample read while paused (live pause, or a replayed pre-crash pause) is left out of avg AND `maxHeartRate` and goes to `TrainingSession.pausedPeakHeartRate` (optional, both model copies). *Unverified on device; diagnosis from code (the max used to be updated regardless of `isPaused`).*
- **Max HR on the watch** (same rule as the phone): `HealthKitAuthService.updateAgeFromHealthKit()` stores the Health age in the watch App Group `userAge` and never writes `userMaxHeartRate` (that key holds only the phone-synced typed value, `maxHR`). An older build froze the Tanaka estimate there; it is cleared when it equals the estimate for the year-only age (now or a year ago).
- **Workouts started from the iPhone** carry an optional `phoneSessionId` in the start message. The watch keeps it on the running workout (`WatchWorkoutManager.phoneSessionID`; workouts started on the watch have none) and, once the start finishes, answers `["action": "workoutStarted", "phoneSessionId", "sessionId": <watch session id>]`, or `workoutStartIgnored` when the start failed. A start that arrives while another workout runs or starts is ignored and also answered with `workoutStartIgnored`. Replies go by sendMessage when the phone is reachable and always by transferUserInfo, and the phone drops duplicates. The id survives a crash: every checkpoint writes it to the sidecar UserDefaults key `activeWorkoutPhoneSessionID` (`[watch session id: phone id]`, removed with the backup), and `resumeRecoveredSession` restores it only when the backup's id matches, so a phone Discard or id-carrying stop still reaches a crash-resumed workout; the resume then skips the watch-originated `workoutStarted`, like a phone-started start. *Unverified on device.* A remote `stop` that carries a `phoneSessionId` stops only the workout with that id; a stop without one (older phone builds) works as before. The watch-originated `workoutStarted` (with `activityType`) now also carries `sessionId`, and it is not sent for a workout the phone started, because the phone reads `activityType` without `phoneSessionId` as a start made on the watch.
- **Discard from the iPhone**: `["action": "discardWorkout", "sentAt": Double, "phoneSessionId": String]` (sendMessage + transferUserInfo, so usually twice). The decision is `Shared/PhoneDiscardRule.swift` (tested). The watch discards only when `phoneSessionId` equals the running workout's id. A missing or different id is ignored, so a phone Discard never drops a workout started on the watch, including one from an older phone build that sends no id. A matching Discard that arrives while the workout is still starting is held, then applied when the start finishes (`WatchSyncCoordinator.workoutStartFinished()`). The 120 s age limit still applies, but the start-time check does not, because the id already proves which workout it is. An applied Discard calls `WatchWorkoutManager.discardWorkout(sentAt:)`: `workoutBuilder.discardWorkout()` + `routeBuilder.discard()`, then `stopWorkout()` (ends the session, clears the backup). Nothing goes to Health or the phone, no summary. On the normal (not held) path it is also ignored when no workout runs, when it is older than 120 s, or when the running workout started more than 5 s after `sentAt`. *Unverified on device: HK accepting `discardWorkout()` on a running live builder.*
- **Crash/kill recovery RESUMES the workout** (2026-10): `WatchAppDelegate.handleActiveWorkoutRecovery()` (`@WKApplicationDelegateAdaptor` in `ShuttlXWatchApp.swift`) and the root `onAppear` both call the idempotent `beginLaunchRecovery()`. `recoverOrphanedHKSession()` gets the live session via `recoverActiveWorkoutSession` (5s timeout); a `.running`/`.paused` session goes to `resumeRecoveredSession(_:)` — delegates, builder, a fresh `HKLiveWorkoutDataSource` and route builder are reattached, and timer/sensors/15s checkpoint continue under the crash backup's session id. Active time comes from `builder.elapsedTime(at:)`; the backup restores segments/steps/splits/route/mode (the checkpoint now carries `templateID`, `programName`, `sportType`, `sessionMode`, `recoveryReport`). HR and energy/distance are NOT seeded from the backup: the HR query replays from the start (anchor nil) and builder statistics are cumulative. Any other state, or a failed auth, falls back to finalizing (`endCollection` + `finishWorkout`); if no session is recovered, the backup is sent.
- **Finalizing an orphan** (any state that is not resumed): `endCollection(at:)` uses the matching backup's last checkpoint `endDate` (not launch time), and `HKMetadataKeyExternalUUID` + `com.shuttlx.sessionID` = backup id are added before `finishWorkout` so the iPhone Health importer matches it. No matching backup → `Date()`, no ids. The normal save also writes `com.shuttlx.sessionID`.
- **Resumed session details**: pause spans come from `builder.workoutEvents` (pause/resume + motion) into `pauseSpans`; replayed HR samples inside them are left out of avg AND peak and the spans go to the metrics ledger. The kill → relaunch gap (backup `endDate` → now) is its own `.unknown` segment. `autoPauseReason` is restored when the session is paused (sidecar UserDefaults key `activeWorkoutAutoPauseReason`, written with every checkpoint, removed with the backup). *Unverified on device: HK accepting a past `endCollection` date and recording pause events in `workoutEvents`.*
- `saveRecoveredSession` **always** hands the backup to `sendSessionToiOS` — "already in sessions.json" means stored on the watch, not delivered. iOS dedups by id, so resending is safe.
- **Distance + energy come from the live builder** (`didCollectDataOf` → `applyBuilderDistance` / `applyBuilderEnergy`): `distanceWalkingRunning` / `distanceCycling` / `distanceSwimming` and `activeEnergyBurned` `statistics(for:).sumQuantity()`. There is no anchored energy query any more (it was unfiltered and summed other sources). Per-phase energy: each builder increment becomes one ledger span. Pedometer = steps/cadence + distance/pace fallback until the builder reports a non-zero distance; on that switch the pace window is cleared so the two sources never mix.
- **Pedometer restarts from resume time** with a captured step/distance offset — paused steps are never counted.
- **Indoor sessions** (`sessionLocationType == .indoor`: gym recovery, elliptical, cross-training) never start CoreLocation; the guard lives in `startLocationUpdates()` and `requestLocationAndStartUpdates()`.
- **Long-workout safety prompt**: at 3h50m ACTIVE time, `SafetyPromptView` (an overlay on `TrainingView`, not a `fullScreenCover`, so no system close button can dismiss it) shows "Still training?" with Continue / End & Save, plays `.notification` and checkpoints right away. Continue re-arms it 60 min later; no answer within 5 active minutes → `finishAndSave(autoEnded: true)` (sets `TrainingSession.autoEnded = true`, a defaulted optional in both copies). Pure logic: `Shared/SafetyPromptSchedule.swift` (tested in `tests/ShuttlXTests/SafetyPromptScheduleTests.swift`). Ticks don't run while paused, so pause freezes both the threshold and the timeout.

## Heart Alerts, Auto-Pause, Activity Switch

- **Alerts** (`HeartAlertEvaluator`, run from the workout tick): above limit, below low limit, signal lost, no motion, and `suddenJump` (`alertSuddenJump`, default OFF in `HeartSafetySettings`; settingsVersion 1 resets older saves to off once). A haptic always fires; a watch notification posts only when the app is not frontmost; every alert goes to the phone as `heartAlert`.
- **Heart-rate samples and pauses**: each sample is judged by its own date, not by when HealthKit delivered it (delivery can lag seconds or more). A sample dated inside a finished pause (`pauseSpans`, which holds live pauses added on resume plus the spans recovered after a crash) or after the current pause began counts only toward `pausedPeakHeartRate`. Every other sample counts toward the average and peak. The rule is `Shared/PausedSample.swift`, tested with delayed delivery in `PausedSampleTests`.
- **Sudden jump = two real samples** (opt-in: off by default, a jump start expires after 10 s without a confirming sample): the evaluator sees a new sample when `lastHRDate` advances (not per tick). It fires when two samples ≥ 5 s apart, with no lower one between, both sit ≥ 40 bpm above the lowest sample of the 10 s before the first. The second sample must come within 10 s of the first (`jumpWindow`), otherwise the first is forgotten. Before that rule, a spike followed by minutes without samples could be "confirmed" by the next sample. One spike never fires; a stale (replayed) sample never confirms. 2 min cooldown.
- **While paused** a 5 s `pausedAlertTimer` (main-queue DispatchSourceTimer, started in `applyPauseState`, also for a paused crash-recovered session; stopped on resume/stop) runs `evaluateHeartAlerts(paused: true)`: only above-limit and signal-lost, re-alerting (haptic + `heartAlert`) every 60 s while the condition holds — including after the no-motion auto-pause. No motion never re-fires; below-low and sudden jump wait for the resume (which resets the evaluator).
- **Notification permission** is requested at every workout start (fire-and-forget, after HealthKit auth; no-op once answered) — not in the alert path, which can't prompt with the wrist down.
- **No-motion auto-pause**: 60 s without an HR sample and without motion pauses the workout with reason `noMotion` (`autoPauseReason`). Only when CoreMotion + pedometer run (`hasMotionSensing`: running / walking sports and gym recovery); elliptical, cross-training, cycling, swimming, hiking and other never auto-pause (above-limit and signal-lost still alert). It is a heuristic: there is no public wrist-detection API. *Unverified: behaviour with the watch off the wrist (device test pending).*
- **Zone word**: with a synced heart limit, the one-word zone (EASY / STEADY / HARD, cut-offs at 70% and 90% of the limit) takes the arc's slot beside the BPM value. Without a limit the arc stays.
- **Activity auto-switch**: `checkSpeedActivity()` classifies on-foot vs cycling from GPS speed and cadence (`SpeedActivityClassifier`, with hysteresis) every 5 s (`speedCheckInterval`; `averageSpeed(of:)` walks `routePoints` backwards, no allocation). `averageSpeed` needs the GPS fixes to COVER the 30 s window (history past it, no gap over `maxFixGap` = 15 s, at least 2 speed fixes), not a fix count: at walking pace the 10 m distance filter gives ~4 fixes per 30 s, and the old 15-fix rule kept a rider who got off the bike on CYCLE (`ActivityClassifierTests.testAverageSpeedAtWalkingPaceCoversWindow`). A pause or GPS dropout inside the window still gives no reading. Unknown cadence is never cycling below 6.5 m/s (23 km/h); a first cycling reading never commits — it holds 60 s like any switch into cycling (first on-foot reading still commits at once). Slow walking after cycling: with the 10 m distance filter a slow walk gives a fix only every 15 s or more, so `averageSpeed` never returns a reading and the segment used to stay on CYCLE. While cycling with no speed reading, `SpeedActivityClassifier.gapVerdict` feeds "on foot" into the same 60 s hold when there is on-foot evidence: a CoreMotion walking/running reading no older than 60 s, or a step cadence of at least 60 spm. A stop at a red light, or a GPS dropout while riding, has neither, so cycling stays. Back on foot: a CoreMotion reading ≤ 60 s old re-earns run/walk; without one, `footFallback` commits the speed classifier's own run/walk (`classifier.override`). *Unverified: thresholds are not yet tuned on real sessions.*
- **Effort**: the post-workout RPE is written to `effortRPE` through `WatchSyncCoordinator.updateSessionEffort`, which also sends the `updateSessionEffort` message to the phone (`sendSessionEffort`).

## Sync

- Watch-side sync is in `WatchSyncCoordinator.swift` (~1,200 lines)
- Phone-side sync is in iOS `PhoneSyncCoordinator.swift` (~1,130 lines)
- Both must handle offline gracefully — queue and retry
- Theme sync: `handleIncomingPayload` handles `"syncTheme"` action from iPhone
- **workoutStopped** (watch → phone, sendMessage + transferUserInfo, from `stopWorkout()` incl. discard) carries `sessionId` (UUID string of the stopped workout; optional, older builds omit it) next to `timestamp`.
- **Incoming payload bounds** (`WatchSyncCoordinator`): `maxHR` outside `HeartLimits.maxHRRange` (except 0 = clear) is rejected; `heartSafetyData` over 8 KB is ignored, decoded settings are `sanitized()` and a `noMotionSeconds` outside 15...600 falls back to 60; templates (`templatesData` and remote-start `templateData`) must pass `isValidTemplate` (at least one step, ≤ 100 steps per block, repeat 1...50, every step 1 s...4 h, name ≤ 200 chars), invalid ones are dropped and the list is capped at 200; a purge `ts` that is not finite or more than 24 h ahead is ignored (it would block every later purge).
- **Purge** (`["action": "purgeSessions", "scope": "all"|"sessions", "ts": Double]`, sendMessage or transferUserInfo): `handlePurgeRequest` drops `ts` ≤ `lastAppliedPurgeTS`, stores the request (`deferredPurge`, merged: newest ts, widest scope) and `applyDeferredPurgeIfPossible()` runs it unless a workout is starting/running (also called from `stopWorkout()` and after launch recovery). It deletes sessions that ENDED before `min(ts, now)` from sessions.json, the pending queue and `sessions_corrupt_*` copies, cancels their outstanding WC transfers; scope `all` also deletes `workout_templates.json` (the built-in fallback template returns). The crash backup is never touched.
